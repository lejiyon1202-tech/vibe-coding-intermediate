### 섹션 1: CLAUDE.md (S03~S05)

#### WHAT — CLAUDE.md가 뭔가요?

> 매 대화마다 같은 배경을 설명하고 있다면, CLAUDE.md가 그 반복을 끝낼 수 있습니다.

CLAUDE.md는 Claude Code에게 "항상 기억해야 할 것"을 적어두는 파일입니다.

대화를 새로 시작해도, 다른 프로젝트로 이동해도 — CLAUDE.md에 적힌 내용은 Claude Code가 항상 읽고 시작합니다.

**4계층 구조** (읽히는 순서):
```
Managed Policy (Anthropic 운영 기준 — 변경 불가)
    ↓
Project (프로젝트 폴더 내 CLAUDE.md — 팀 공유)
    ↓
User (~/.claude/CLAUDE.md — 내 개인 설정)
    ↓
Local (.claude/CLAUDE.md — 이 세션만)
```

> 아래로 내려올수록 더 구체적인 내용. 아래 계층이 위 계층을 덮어씁니다.

**Auto Memory**: Claude Code가 대화 중 중요한 내용을 자동으로 User 계층에 저장합니다. "기억해줘"라고 말하지 않아도 자동으로 저장되는 기능입니다.

#### HOW — 직접 작성해봅시다

가장 자주 쓰는 Project 계층부터 시작합니다.

```bash
# 프로젝트 폴더 루트에 CLAUDE.md 파일 생성
touch CLAUDE.md
```

**기본 템플릿:**
```markdown
# 프로젝트 이름

## 역할 정의
당신은 [직무/역할]입니다. [맥락 1~2줄].

## 절대 규칙
- [금지 사항 1]
- [금지 사항 2]

## 선호 스타일
- 언어: 한국어
- 어조: 비즈니스 존댓말
- 출력 형식: [마크다운/표/코드]

## 자주 쓰는 정보
- 회사명: [OO]
- 담당 시스템: [OO]
- 팀 컨벤션: [OO]
```

**HR 담당자 예시:**
```markdown
# HR 업무 보조

## 역할
당신은 HR 전문가 보조 AI입니다. 교육 기획, 공고 작성, 설문 분석을 담당합니다.

## 절대 규칙
- 개인정보(이름, 사번, 연봉)는 절대 출력하지 않습니다
- 채용 공고에 나이·성별 조건 포함 금지

## 선호 형식
- 교육 기획안: Kirkpatrick 4단계 구조
- 공고 작성: 두괄식 + 핵심 자격요건 3개 이내
```

#### WHEN — 언제 쓰면 좋을까요?

CLAUDE.md가 필요한 순간:
- **매번 같은 설명 반복할 때** — "우리 회사 코딩 스타일은 이래" 같은 걸 매 대화마다 설명한다면 → CLAUDE.md에 고정
- **AI가 자꾸 다른 방식으로 할 때** — 원하는 형식·어조·규칙을 CLAUDE.md에 못 박기
- **팀과 AI 설정을 공유하고 싶을 때** — Project 계층 CLAUDE.md는 git으로 팀 전체 공유 가능

CLAUDE.md가 굳이 필요 없는 순간:
- 일회성 질문
- 프로젝트와 무관한 개인적 궁금증

#### VALUE — 쓰기 전 vs 후

| 상황 | CLAUDE.md 없음 | CLAUDE.md 있음 |
|------|--------------|--------------|
| 새 대화 시작 | 배경 설명 5분 | 바로 본론 |
| 형식 오류 | 매번 수정 요청 | 처음부터 원하는 형식 |
| 팀 공유 | 각자 다른 AI 사용 | 동일한 설정으로 팀 통일 |

#### ✅ [1단계 체크] 섹션 1 핵심 확인

- [ ] CLAUDE.md 4계층 구조를 말할 수 있다 (Managed Policy → Project → User → Local)
- [ ] 내 업무에 맞는 CLAUDE.md를 직접 작성했거나 작성 계획이 있다
- [ ] Auto Memory가 어떤 계층에 저장되는지 안다

### 섹션 2: Skills (S06~S08)

#### WHAT — Skills가 뭔가요?

> "이 형식으로 다시 써줘"를 세 번 넘게 말했다면, 그 요청을 Skills로 등록할 때가 됐습니다.

Skills는 Claude Code에게 "이 명령어를 쓰면 항상 이렇게 해줘"라고 등록하는 기능입니다.

`/명령어` 형식으로 호출하면, 미리 정의한 프롬프트와 동작이 실행됩니다.

**단축키를 만드는 것과 같습니다.** 복잡한 요청을 짧은 명령어로 압축합니다.

#### HOW — SKILL.md 직접 작성

Skills는 `.claude/skills/` 폴더에 마크다운 파일로 저장합니다.

```bash
mkdir -p .claude/skills
```

**기본 SKILL.md 구조:**
```markdown
---
name: 명령어이름
description: 이 Skills가 하는 일 한 줄 설명
---

# 지시사항
[Claude Code에게 전달할 상세 지시]

# 입력값
$ARGUMENTS — 호출 시 추가로 입력한 텍스트

# 출력 형식
[원하는 출력 형식 명시]
```

**HR 담당자 예시 — 교육 기획안 생성:**
```markdown
---
name: 교육기획
description: 주제와 대상을 입력하면 교육 기획안 초안을 생성합니다
---

# 지시사항
교육 기획안을 작성합니다. Kirkpatrick 4단계 평가 모델을 적용하고,
학습 목표는 Bloom의 분류학 기반으로 작성합니다.

# 입력값
주제·대상·시간: $ARGUMENTS

# 출력 형식
| 항목 | 내용 |
|------|------|
| 과정명 | |
| 대상 | |
| 학습 목표 | |
| 커리큘럼 | |
| 평가 방법 | |
```

> **팁**: Skills 파일 저장 후 바로 `/명령어`로 사용 가능합니다. 세션 재시작 불필요.
> 단, `.claude/skills/` 디렉토리를 새로 만들었을 때는 한 번 재시작 필요.

#### WHEN — 언제 쓰면 좋을까요?

Skills가 효과적인 경우:
- **반복 요청이 3번 이상 될 때** — "이 형식으로 다시 써줘"를 세 번 넘게 말했다면 → Skills로 등록
- **팀 표준 작업이 있을 때** — 팀 전체가 같은 방식으로 쓰는 작업 → 공유 Skills로 등록
- **복잡한 프롬프트를 매번 쓸 때** — 긴 지시를 `/명령어`로 압축

#### VALUE — Skills 도입 전 vs 후

| | 전 | 후 |
|--|--|--|
| 교육 기획안 초안 | 형식 설명 + 요청 5분 | `/교육기획 리더십 / 팀장 / 4시간` 10초 |
| 팀 통일성 | 각자 다른 방식 | SKILL.md git 공유 → 팀 표준화 |
| 신입 온보딩 | "이렇게 써야 해" 설명 반복 | `.claude/skills/` 폴더 공유 끝 |

#### ✅ [1단계 체크] 섹션 2 핵심 확인

- [ ] `.claude/skills/` 폴더 구조를 알고 있다
- [ ] 내 업무에서 Skills로 등록할 만한 반복 작업을 1개 이상 떠올릴 수 있다
- [ ] 세션 재시작 없이 Skills가 반영되는 조건을 안다

### 섹션 3: Hooks (S09~S11)

#### WHAT — Hooks가 뭔가요?

> 실수로 위험한 명령어를 실행할까봐 걱정된다면, Hooks가 자동으로 막아줄 수 있습니다.

Hooks는 Claude Code가 특정 동작을 하기 전/후에 자동으로 실행되는 명령어입니다.

"파일 저장하면 자동 포맷"처럼, AI가 도구를 쓸 때 자동으로 추가 작업이 실행됩니다.

**4가지 이벤트 타입:**
- `PreToolUse` — 도구 실행 직전 (위험 명령어 차단 등)
- `PostToolUse` — 도구 실행 직후 (자동 포맷, 알림 등)
- `Stop` — Claude 응답 완료 시 (작업 완료 알림)
- `SubagentStop` — 서브에이전트 완료 시

#### HOW — settings.json에 설정

`.claude/settings.json` 파일에 작성합니다.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "cmd=$(jq -r '.tool_input.command // empty'); echo \"$cmd\" | grep -qi 'rm -rf' && echo '위험 명령어 감지!' || true"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write",
        "hooks": [
          {
            "type": "command",
            "command": "fp=$(jq -r '.tool_input.file_path // empty'); echo \"[$(date '+%Y-%m-%d %H:%M:%S')] 파일 저장: $fp\" >> ~/작업로그.txt"
          }
        ]
      }
    ]
  }
}
```

**exit 2 차단 패턴** (위험 명령어 실행 자체를 막는 방법):
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "cmd=$(jq -r '.tool_input.command // empty'); if echo \"$cmd\" | grep -q 'rm -rf'; then echo '위험 명령어 차단'; exit 2; fi"
          }
        ]
      }
    ]
  }
}
```

> **exit 2의 의미**: hook이 exit 2로 종료되면 Claude Code가 해당 도구 실행을 **완전히 중단**합니다. (exit 0 = 정상 통과, exit 1 = 경고만, exit 2 = 강제 차단)

#### WHEN — 언제 쓰면 좋을까요?

Hooks가 필요한 순간:
- **실수로 위험한 명령어 실행할까봐 걱정될 때** — exit 2 차단 패턴
- **작업 로그를 자동으로 남기고 싶을 때** — PostToolUse 로그 기록
- **파일 저장할 때마다 자동 포맷 확인** — PostToolUse + prettier

Hooks보다 CLAUDE.md가 더 나은 경우:
- 단순한 "이렇게 해줘" 규칙 → CLAUDE.md로 충분
- Hooks는 실제 명령어 실행이 필요할 때만

#### VALUE — Hooks 도입 전 vs 후

| 상황 | Hooks 없음 | Hooks 있음 |
|------|-----------|-----------|
| 위험 명령어 | 실수로 실행 가능 | exit 2로 자동 차단 |
| 작업 이력 | 기억에 의존 | 자동 로그 파일 |
| 반복 검증 | 매번 수동 확인 | 저장 시 자동 실행 |

#### ✅ [1단계 체크] 섹션 3 핵심 확인

- [ ] Hooks 4가지 이벤트 타입을 말할 수 있다
- [ ] exit 0·exit 1·exit 2의 차이를 안다
- [ ] 내 업무에서 자동화하고 싶은 반복 동작을 1개 이상 떠올릴 수 있다

### 섹션 4: Subagents (S12~S14)

#### WHAT — Subagents가 뭔가요?

> 하나의 Claude Code 대화가 너무 복잡해졌다면, 전문 역할 Subagent 팀을 꾸릴 때입니다.

Subagents는 Claude Code 안에서 실행되는 전문 역할 AI입니다.

메인 Claude가 복잡한 작업을 여러 조각으로 나눠 각 Subagent에게 위임합니다.

**내장 Subagents (별도 설정 없이 바로 사용):**
- `Explore` — 코드베이스·파일 탐색 전문
- `Plan` — 작업 계획·설계 전문
- `general-purpose` — 범용 작업

**커스텀 Subagents**: `.claude/agents/` 폴더에 직접 정의 가능

#### HOW — 내장 Subagents 활용

Claude Code에게 자연어로 요청하면 자동으로 적절한 Subagent가 선택됩니다:

```
"이 프로젝트 폴더 전체 구조를 파악해줘"  → Explore 자동 발동
"이 기능 구현하기 전에 계획 먼저 세워줘" → Plan 자동 발동
```

**커스텀 Subagent 만들기:**
```markdown
# .claude/agents/회의록정리.md

---
name: 회의록정리
description: 회의 내용을 입력하면 액션 아이템과 결정사항을 정리합니다
---

## 역할
당신은 회의록 정리 전문가입니다.

## 출력 형식
### 결정 사항
- [항목]

### 액션 아이템
| 담당자 | 할 일 | 기한 |
|--------|------|------|
```

#### WHEN — 언제 Subagents를 쓸까요?

Subagents가 효과적인 경우:
- **작업이 크고 단계적일 때** — 전체 프로젝트 분석 후 리포트 작성
- **독립적인 전문 역할이 필요할 때** — 코드 작성 ≠ 코드 리뷰 (분리)
- **긴 작업에서 컨텍스트가 부족할 때** — Subagent는 독립 컨텍스트로 실행

Subagents가 과한 경우:
- 간단한 1회성 질문 → 그냥 Claude에게 바로 질문
- 한 두 줄 생성 → Subagents 불필요

#### VALUE — Subagents 도입 전 vs 후

| | 전 | 후 |
|--|--|--|
| 복잡한 분석 | 하나의 긴 대화에서 처리 | 전문 Subagent에게 위임 |
| 코드 + 리뷰 | 같은 AI가 작성·리뷰 (관대화 위험) | 작성 AI ≠ 리뷰 AI |
| 반복 작업 | 매번 역할 설명 | 커스텀 Subagent로 등록 |

#### ✅ [1단계 체크] 섹션 4 핵심 확인

- [ ] Explore·Plan·general-purpose 내장 Subagents를 알고 있다
- [ ] `.claude/agents/` 폴더에 커스텀 Subagent 파일 작성 방법을 안다
- [ ] 내 업무에서 "독립 역할 분리"가 필요한 작업을 1개 이상 떠올릴 수 있다

### 섹션 5: MCP (S15~S17)

#### WHAT — MCP가 뭔가요?

> 하루에도 여러 번 Claude ↔ GitHub ↔ Slack을 왔다 갔다 한다면, MCP로 이 도구 전환을 없앨 수 있습니다.

MCP(Model Context Protocol)는 Claude Code에 외부 도구·서비스를 연결하는 표준 방식입니다.

마치 스마트폰 앱처럼, 필요한 도구를 설치해서 Claude Code의 능력을 확장합니다.

**공식 Registry**: `https://code.claude.com/docs/en/mcp` — 3,000개 이상의 MCP 서버 목록

> **주의**: mcp.so는 Anthropic 공식 서버가 아닌 커뮤니티 허브입니다. 공식 문서(code.claude.com)를 우선 참조하세요.

#### HOW — MCP 서버 추가

```bash
# 명령어로 추가 (project 범위 = 이 프로젝트에만 적용)
claude mcp add github --scope project

# 사용자 범위 (내 모든 프로젝트에 적용)
claude mcp add slack --scope user

# 현재 설정된 서버 확인
claude mcp list
```

`.claude/settings.json`으로 직접 설정:
```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "환경변수로 관리 — 코드에 직접 입력 금지"
      }
    }
  }
}
```

> **중요**: API 토큰은 반드시 환경변수로 관리하세요. settings.json에 직접 입력하면 git 공유 시 토큰이 노출됩니다.

**신기능 알림 (Claude Code v2.1.118)**: MCP 도구를 Hooks에서 직접 호출하는 기능이 추가됐습니다. 자세한 내용은 고급 교안 참조.

#### WHEN — 어떤 MCP 서버를 연결할까요?

자주 쓰는 서비스별 추천:
| 반복 작업 | 추천 MCP 서버 |
|---------|------------|
| GitHub PR 확인·코드 리뷰 | `@modelcontextprotocol/server-github` |
| Slack 메시지 발송 | `@modelcontextprotocol/server-slack` |
| Google Drive 파일 관리 | `@modelcontextprotocol/server-google-drive` |
| DB 직접 조회 | `@modelcontextprotocol/server-postgres` |

연결 전 체크리스트:
- [ ] 이 도구를 하루 몇 번 전환하는가? (3번 미만이면 MCP 효과 낮음)
- [ ] API 토큰은 안전하게 환경변수로 관리할 수 있는가?
- [ ] 팀과 공유가 필요한가? (settings.json에서 토큰 제거 후 공유)

#### VALUE — MCP 도입 전 vs 후

| 작업 | 전 | 후 |
|------|--|--|
| PR 상태 확인 | GitHub 열기→클릭→복사 | "PR #42 상태 알려줘" |
| Slack 공지 | Slack 앱→채널→작성→전송 | "이 내용 #개발팀에 보내줘" |
| DB 조회 | SQL 작성→실행→해석 | "이번 달 미완료 과제 목록 뽑아줘" |

#### ✅ [1단계 체크] 섹션 5 핵심 확인

- [ ] MCP 서버를 추가하는 명령어(`claude mcp add`)를 안다
- [ ] API 토큰을 안전하게 관리하는 방법(환경변수)을 안다
- [ ] 내 일상 업무에서 MCP로 자동화하고 싶은 도구 전환 1개를 떠올릴 수 있다

## FAQ 10건

**Q1. CLAUDE.md를 얼마나 자세히 써야 하나요?**
처음에는 짧게 시작하세요. 3~5줄이면 충분합니다. AI가 엉뚱한 결과를 냈을 때마다 그 이유를 CLAUDE.md에 추가하는 방식으로 점점 보완하면 됩니다. 처음부터 완벽한 CLAUDE.md를 만들려다 아무것도 못 쓰는 것보다 훨씬 낫습니다.

**Q2. Skills, CLAUDE.md, Hooks 중 뭐부터 시작해야 할까요?**
CLAUDE.md → Skills → Hooks 순서를 추천합니다. CLAUDE.md는 가장 기본적인 "맥락 설정"이고, 이게 있어야 나머지 기능도 일관되게 작동합니다.

**Q3. Hooks가 잘못 설정되면 Claude Code가 아예 안 되는 건 아닌가요?**
exit 1(경고)을 쓰면 Claude Code가 멈추지 않고 경고만 출력하며 계속 진행합니다. exit 2(강제 차단)는 특정 도구 실행만 막습니다. Hooks 설정이 잘못됐다면 settings.json에서 hooks 섹션을 지우면 바로 원상 복구됩니다.

**Q4. 여러 프로젝트에서 같은 Skills를 쓰고 싶어요.**
User 계층(~/.claude/skills/)에 저장하면 모든 프로젝트에서 사용 가능합니다. 특정 프로젝트에서만 쓰고 싶으면 해당 프로젝트의 .claude/skills/에 저장하세요.

**Q5. MCP 서버 연결 후 팀과 공유하려면 어떻게 하나요?**
settings.json에서 API 토큰 값은 환경변수 이름만 남기고 실제 값은 지운 채로 공유하세요. 예: `"GITHUB_TOKEN": "$GITHUB_TOKEN"`. 팀원 각자가 자신의 환경에서 해당 환경변수를 설정하면 됩니다.

**Q6. Subagents를 쓰면 시간이 더 걸리지 않나요?**
짧은 작업은 맞습니다. 단, 복잡하고 큰 작업은 오히려 빠릅니다. Subagents는 병렬 실행이 가능해서, 큰 프로젝트 분석·다단계 작업에서 전체 시간이 줄어듭니다.

**Q7. CLAUDE.md에 민감한 정보(비밀번호, 개인정보)를 넣어도 되나요?**
절대 안 됩니다. CLAUDE.md는 평문 텍스트 파일이라 git에 올라가거나 다른 사람이 볼 수 있습니다. 민감 정보는 환경변수(.env 파일)로 관리하세요.

**Q8. Skills 파일명은 어떻게 정해야 하나요?**
name 필드에 정의한 값이 `/명령어`의 명령어 이름이 됩니다. 파일명은 name과 같거나 비슷하게 유지하면 관리하기 편합니다. 한글도 가능하지만 영문 소문자+하이픈 형식 권장합니다.

**Q9. Hooks에서 도구 정보를 어떻게 받나요?**
Hooks는 **stdin JSON 페이로드**로 도구 정보를 받습니다. `tool_name` (도구 이름), `tool_input` (입력값), `tool_response` (결과값) 필드를 `jq` 등으로 파싱해서 사용하세요. 예: `cmd=$(jq -r '.tool_input.command')`. 별도 제공 환경변수 5종(`$CLAUDE_PROJECT_DIR`·`$CLAUDE_PLUGIN_ROOT`·`$CLAUDE_PLUGIN_DATA`·`$CLAUDE_ENV_FILE`·`$CLAUDE_CODE_REMOTE`)도 활용 가능합니다. 상세 내용은 `code.claude.com/docs/en/hooks` 참조.

**Q10. 이 자료에서 배운 내용이 회사 보안 정책에 위반될 수 있나요?**
가능합니다. MCP 서버는 외부 서비스 연결이므로, 연결 전 회사 보안팀에 확인하세요. CLAUDE.md와 Skills는 로컬 파일이라 비교적 안전하지만, 민감한 정보를 넣지 않는 원칙을 지키는 것이 중요합니다.

**Q11. CLAUDE.md가 점점 길어지는데, 어느 시점에 정리해야 할까요?**
체감 기준은 두 가지입니다. ① 스크롤 없이 전체가 안 보일 때, ② 새 규칙을 추가하다가 기존 규칙과 충돌이 생길 때입니다. 이때는 핵심 규칙만 CLAUDE.md에 남기고, 상세 맥락은 별도 파일(예: `context/team-conventions.md`)에 분리한 뒤 `@파일명`으로 참조하세요. 핵심 10줄 + 참조 파일 구조가 실전에서 가장 관리하기 쉽습니다.

**Q12. Skills 명령어 이름이 기존 명령어와 겹치면 어떻게 되나요?**
더 구체적인 계층(Project > User)이 우선 적용됩니다. 예를 들어 User 계층 Skills와 Project 계층 Skills의 이름이 같으면 Project 계층이 이깁니다. 팀 공유 Skills는 `/팀명-명령어` 형식 접두어를 권장합니다. `/memory` 같은 Claude Code 내장 명령어와 같은 이름은 피하세요.

**Q13. Hooks에서 Slack이나 사내 시스템에 알림을 보낼 수 있나요?**
가능합니다. `command` 타입 대신 `http` 타입을 쓰면 외부 URL로 POST 요청을 보낼 수 있습니다. 단, 핵심 작업 흐름을 막지 않도록 `PostToolUse` 또는 `Stop` 이벤트에서만 쓰는 것을 권장합니다. 응답이 느린 외부 API를 `PreToolUse`에 넣으면 Claude Code 작업 전체가 대기 상태가 됩니다.

**Q14. 커스텀 Subagent를 팀원과 공유하려면 어떻게 하나요?**
`.claude/agents/` 폴더를 git에 커밋하면 됩니다. 팀원이 저장소를 clone하면 동일한 Subagent를 즉시 사용할 수 있습니다. 단, Subagent 파일에 API 토큰 등 민감 정보를 직접 넣지 않도록 주의하세요. Subagent 파일은 순수 역할 정의 파일로만 관리하고, 민감 정보는 항상 환경변수로 분리합니다.

**Q15. MCP 서버가 갑자기 응답하지 않으면 어떻게 되나요?**
Claude Code가 해당 MCP 서버의 도구를 사용하지 못하고 에러를 반환합니다. 다른 작업에는 영향이 없습니다. `claude mcp list`로 서버 상태를 확인하고, 문제가 있으면 `claude mcp remove [이름]` 후 재추가하세요. 사용하지 않는 MCP 서버는 정기적으로 정리해두는 것이 성능과 보안 모두에 좋습니다.

### ❌ 안티패턴 1: CLAUDE.md에 너무 많이 써서 역효과

```markdown
(계속)
```

**왜 문제인가:** 너무 길면 Claude가 중간 내용을 놓칩니다. 모순된 지시가 있으면 예측 불가능하게 동작합니다.

**올바른 방법:** 핵심 규칙만 3~10개 이내로 유지. "항상 정중하게"처럼 Claude 기본 동작과 같은 건 굳이 쓸 필요 없습니다.

**올바른 방법:** 등록 기준을 정하세요. **한 달에 3번 이상 쓰는 작업만 Skills로 등록**합니다. 월 1회 `/skills/` 폴더를 열어 쓰지 않는 파일은 삭제합니다. 10개 이하로 유지하면 명령어를 외울 수 있습니다.

### ❌ 안티패턴 7: 커스텀 Subagent 하나에 너무 많은 역할 부여

**흔한 실수:**
```markdown
---
name: 만능-에이전트
description: 회의록 정리, 보고서 작성, 코드 리뷰, 메일 초안, 번역 전부 담당

```

**왜 문제인가:** Subagents의 강점은 "하나의 역할에 집중"입니다. 역할이 많을수록 각 작업의 품질이 낮아집니다. 긴 역할 설명은 컨텍스트를 낭비합니다.

**올바른 방법:** Subagent 하나에 역할 하나. 회의록 정리·보고서 작성·코드 리뷰는 각각 별도 파일로 분리합니다. 복잡한 작업은 여러 Subagent를 순차·병렬 실행으로 나눕니다.

**올바른 방법:** `claude mcp list`로 월 1회 점검. 한 달 이상 사용하지 않은 서버는 `claude mcp remove [이름]`으로 정리합니다. "실제로 매주 쓰는 서버만 연결" 원칙을 지키세요.

### S18 — 개발자 케이스: PR 자동 1차 리뷰

**여러분의 일상을 떠올려 보세요.**

팀원이 PR을 올렸습니다. 오늘도 리뷰가 5개 쌓여 있습니다. 오후 회의도 있고, 다른 기능 개발도 해야 합니다. 급하게 확인하다 보니 네이밍 실수나 중복 로직은 놓치고, 나중에 "왜 이게 통과됐지?" 하는 버그로 돌아옵니다. 리뷰어도 힘들고, 올린 팀원도 미안합니다. 이 반복이 쌓이면 팀 전체가 형식적 리뷰에 익숙해집니다.

**이 상황에서 Claude Code를 어떻게 활용할까요?**

**Before (현재)**:
- PR 올라오면 팀원이 직접 열어서 읽음
- 리뷰 댓글 작성 평균 30~60분
- 급하면 형식적 리뷰 → 버그 나중에 발견 → 재작업

**After (AI 활용 후)**:
- CLAUDE.md에 코드 스타일 가이드·금지 패턴 고정
- Hooks(PreToolUse)로 코드 저장 시 자동 1차 체크
- 팀원은 로직 판단에만 집중, 형식 검토는 AI가 담당

**임팩트** *(추정치·실측 기준 아님)*:
- 리뷰 응답 시간 약 50~60% 단축 예상
- CLAUDE.md 스타일 규칙으로 반복 지적 사항 감소
- "이런 실수는 당연히 잡혔어야 하는데" 하는 리뷰어의 부담감이 줄어듭니다. 사람은 로직 판단에만 집중하고, 형식 검토는 AI가 담당하는 분업 구조가 팀 신뢰를 높입니다.

**여러분의 코드베이스에 적용해보기:**
1. 팀 코드 리뷰에서 자주 반복되는 지적 사항 3개 적어보기
2. CLAUDE.md "코드 스타일" 섹션에 해당 내용 추가
3. 다음 PR 리뷰 요청 시 Claude Code에게 먼저 1차 검토 요청

**[카리나 기술 파트 — CLAUDE.md 코드 스타일 섹션 예시 + Hooks PreToolUse 설정 코드]**

### S19 — 기획자 케이스: 기획서 초안 Skills 자동화

**이런 경험 있으신가요?**

회의가 끝났습니다. 좋은 아이디어들이 많이 나왔는데, 이걸 기획서 형식으로 정리하는 데 2~3시간이 사라집니다. 빈 문서 앞에서 어디서부터 시작해야 할지 막막합니다. 회의 직후 생생했던 아이디어의 온도가 기획서를 타이핑하는 동안 식어갑니다. 초안을 겨우 완성해도 "방향이 맞나?" 하는 의심에 또 한 번 검토를 반복합니다.

**AI로 이 막막함을 없앨 수 있습니다.**

**Before (현재)**:
- 회의 종료 → 메모 정리 → 기획서 양식 열기 → 목적·배경·요구사항 직접 타이핑
- 초안 방향이 맞는지 의심 → 재검토 반복 → 총 2~3시간

**After (AI 활용 후)**:
- Skills에 `/기획서` 명령어 등록
- 회의 핵심 3줄 입력 → 표준 양식 초안 생성
- CLAUDE.md에 회사 기획서 포맷·금지 표현·필수 섹션 고정

**임팩트** *(추정치·실측 기준 아님)*:
- 초안 작성 시간 2~3시간 → 30분 이내 예상
- 팀 기획서 포맷 통일 가능
- 회의가 끝나고 "이걸 언제 다 쓰지" 하는 걱정이 사라집니다. 아이디어의 온도가 식기 전에 초안이 나오면, 이후 검토가 훨씬 빠릅니다.

**여러분의 업무에 적용해보기:**
1. 가장 자주 쓰는 문서 양식 1개 선택 (회의록·기획서·보고서)
2. 해당 양식의 표준 구조를 SKILL.md에 정의
3. `/명령어 [핵심 내용 1~2줄]` 패턴으로 테스트

### S20 — HR/HRD 담당자 케이스: 교육 기획 + 수강 후기 분석

과정 기획안 작성에 반나절, 수강 후기 100건 정리에 또 반나절. 수강 후기는 이미 100건이 쌓였지만, 엑셀로 옮기고 분류하는 작업만 해도 오후가 다 갑니다. 정작 "이 교육이 현업에 실제로 적용됐나?"를 분석하고 다음 과정 방향을 잡는 일은 언제나 나중으로 밀립니다. 행정 처리에 치여서 전략적 판단을 할 시간이 없습니다.

**이 두 가지를 AI에 위임할 수 있습니다.**

**Before (현재)**:
- 교육 기획: 목표·대상·커리큘럼 직접 작성 3~4시간

**임팩트** *(추정치·실측 기준 아님)*:
- 교육 기획 초안 3~4시간 → 1시간 이내 예상
- 수강 후기 분석 반나절 → 10~30분 예상
- 행정 처리 시간이 줄어든 만큼, "이 교육이 실제로 현업에서 어떤 변화를 만들었나?"를 분석하는 전략적 업무에 집중할 수 있게 됩니다. HRD 담당자의 역할이 행정에서 전략으로 이동합니다.

### S21 — 리더·팀장 케이스: 회의록 + 성과 보고서 Subagents 병렬

**팀장님들의 공통 고민입니다.**

주간 회의록 정리 30분 + 월말 성과 보고서 2~3시간. 팀원들 업무를 취합하고, 경영진이 읽기 좋은 언어로 번역하고, 수치를 정리하는 이 작업이 매달 반복됩니다. 문제는 시간만이 아닙니다. 이 시간이 팀원과 1:1 면담, 방향성 논의, 코칭 등 리더로서 진짜 해야 할 일을 밀어냅니다. 리더가 행정 처리에 묶여 있을수록, 팀은 방향을 잃습니다.

**Subagents를 활용하면 이 작업을 동시에 처리할 수 있습니다.**

**Before (현재)**:
- 회의 60분 → 회의록 정리 30분 → 액션 아이템 추출 + 담당자 배분 → 총 90분
- 월말: 팀원 4~5명 업무 취합 → 요약 → 경영진 보고용 변환 → 2~3시간

**After (AI 활용 후)**:
- "회의록 정리" + "성과 요약" 커스텀 Subagents 2개 운용
- 회의록 붙여넣기 → 액션 아이템·담당자·기한 자동 추출
- 팀원 업무 일지 취합 → 경영진 보고서 초안 자동 생성

**임팩트** *(추정치·실측 기준 아님)*:
- 회의 후 정리 90분 → 15~30분 예상
- 월말 보고서 2~3시간 → 30~60분 예상
- 매달 보고서에 쓰던 시간이 팀원 1:1 미팅, 방향성 코칭, 팀 분위기 관리 시간으로 전환됩니다. 리더가 사람에 집중할 수 있을 때 팀 성과가 달라집니다.

**여러분의 업무에 적용해보기:**
1. 최근 회의록 1건을 Claude Code에 붙여넣기
2. "액션 아이템·담당자·기한을 표로 추출해줘" 요청
3. 직접 정리할 때와 시간 비교

**[카리나 기술 파트 — 커스텀 Subagents agents/회의록정리.md + CLAUDE.md 보고서 포맷 설정]**

### S22 — 영업·CS 담당자 케이스: 제안서 초안 + 메일 MCP 반자동화

**영업·CS 담당자라면 익숙한 상황입니다.**

RFP가 왔습니다. 기존 제안서 폴더를 뒤지고, "이 부분은 저번 OO사 제안서에 비슷한 게 있었는데"하며 복사·붙여넣기·수정을 반복합니다. 여기까지만 반나절~하루. 고객 문의 메일은 하루 20~30건, 비슷한 질문인데 매번 새로 씁니다. 이 반복이 쌓이면 영업 담당자의 에너지가 고객과의 진짜 대화가 아닌 문서 만들기에 소진됩니다.

**MCP로 이 작업의 반을 줄일 수 있습니다.**

**Before (현재)**:
- RFP 수신 → 기존 제안서 뒤지기 → 맞춤화 작업 → 반나절~하루
- 고객 문의 메일 20~30건 → 유사 내용 반복 답변 → 2~3시간

**After (AI 활용 후)**:
- MCP(Google Drive) 연결 → 기존 제안서 자동 참조 + 맞춤화 초안 생성
- Skills에 `/고객답변` 등록 → 문의 유형별 템플릿 자동 선택 + 커스터마이징

**임팩트** *(추정치·실측 기준 아님)*:
- 제안서 초안 하루 → 2~3시간 예상
- 반복 메일 답변 2~3시간 → 30~60분 예상
- 문서 만드는 시간이 줄어든 만큼, 고객과 실제 대화하고 니즈를 파악하는 시간이 늘어납니다. 같은 하루지만 고객 접점의 질이 달라집니다.
